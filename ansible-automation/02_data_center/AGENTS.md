# Agent and maintainer notes - 02_data_center

Notes for anyone (person or coding agent) changing the data center track.
Students read the playbooks; maintainers read this file. The project README
(`ansible/README.md`) explains the concepts and design; this file keeps the
implementation detail that used to live in playbook comments.

## Comment convention

- The audience of playbook, inventory and data-model comments is a beginner
  network automation student. Write plain English and explain the idea, not
  the mechanism.
- Every comment block is at most 3 lines. Put API paths, module internals,
  controller quirks, measured behaviour and history here or in the README,
  never in comments.
- Comment-only edits must not change content. Compare the parsed YAML before
  and after (`yaml.safe_load_all`), and run `ansible-playbook --syntax-check`.

## Design decision: L3Outs and cisco.nd

- The handoff used to be built as VRF attachment extensions over the Manage
  API (`06_vrf_lite.yml`). Cisco NaC engineering and PM position that method
  only for customers who already use it, and recommend the L3Out object for
  new work. The track moved to L3Outs after a pod evaluation on 2026-11-12
  (steps 1-10 passed). The full history is in the git commits after tag
  `eval-nd-l3out-base`.
- What changed on the wire: nothing. The sub-interfaces, addresses, VRFs,
  neighbours, route-map and received prefixes matched the old build. The one
  extra line is `local-as 65000` per neighbour.
- `cisco.nd` is a pre-release from `CiscoDevNet/ansible-nd` develop at commit
  `671e596` (galaxy.yml says 1.5.0; the modules are `version_added: 2.0.0`).
  It is pinned in `ansible/collections/requirements-cisco-nd.yml`. The
  bootstrap installs it with `--no-deps` into `ansible/collections/`
  (git-ignored), which only this track's `ansible.cfg` searches. When
  `cisco.nd` 2.0.0 is released, move it to the normal pinned requirements and
  re-test.
- Python: `pydantic` and `jsonpath-ng` are pinned in
  `ansible-automation/requirements.txt`. Upstream pins pydantic 2.12.5; the
  venv runs 2.14.3 (required by `typer`), and the pod run passed on it.
- Before bumping the commit, re-check the open L3Out and links PRs upstream
  (#629, #626, #657 at the time). PR #657 was still changing
  `nd_manage_links`.

## How stages run

- `01_dc_deploy.yml` runs each stage as its own `ansible-playbook` process
  through `tasks/run_stage.yml`. ansible-core keys persistent connections on
  address, port, user, connection type and process ID, not
  `ansible_network_os`. So in one process a `cisco.nd` stage could reuse the
  `cisco.dcnm` httpapi connection stage 02 left open.
- `run_stage.yml` calls the `ansible-playbook` beside `ansible_playbook_python`,
  so a stage uses the same virtualenv as the entry point. `chdir` to the
  collection root makes `ansible.cfg` and the vault password file resolve as
  for a manual run. `failed_when: false` defers the verdict until the log
  file is written.
- The log directory name is fixed with `set_fact`, because a template using
  `now()` is re-evaluated on every use and would split one run's logs.
- Child-process output appears only when a stage finishes. The full output is
  in `evidence/dc-deploy-<run>/<stage>.log`.
- Stages 02 and 06 use `cisco.dcnm` (NaC roles). Stages 03, 04, 05, 07 and 08
  set `ansible_network_os: cisco.nd.nd` per play.

## Stage notes

### 00 - serial discovery
- Use the CHASSIS serial from `show inventory | json`, not `show version` /
  `nxos_facts` (`ansible_net_serialnum`, the supervisor board ID). On Nexus
  9000v they differ, and the wrong one makes controller calls fail with
  "getIDFromSN ... is null". On physical hardware they match, so the bug is
  easy to miss.
- In `show inventory | json` the `name` field arrives with literal quotes
  (`"Chassis"`), so the chassis row is matched by substring.
- The C8000V edge router has no `| json`. `show inventory` text is parsed, and
  the SN sits on the line after the one naming "Chassis". `module R0` carries
  a different serial.
- The validate role only checks that `serial_number` is non-empty, so a
  placeholder or a wrong serial passes validation and fails deep in the create
  role. That is why every switch must answer before anything is written, and
  why stage 02 re-checks for `REPLACE_ME`.
- The generated model's header replaces the `.example`'s leading comments
  (regex `\A---\n(?:#[^\n]*\n)+`). The final assert looks for the
  `# GENERATED BY 00_discover_dc_switch_serials.yml` line, so keep it.
- Roles are substituted from `dc_switches.yml`, anchored on `- name:`, so
  reordering either source cannot misplace a serial or a role.
- The `dc_fabric_switches` group is declared empty in `static_inventory.yml`
  so that `group_vars/dc_fabric_switches/` binds to the hosts `add_host`
  creates.

### 03 - fabric settings
- `nd_manage_fabric_ibgp_vxlan state: merged` sends only the declared keys.
  The argspec has no defaults, unset options are stripped before the diff, and
  the update starts from the controller's copy. Stage 02's values are left
  alone, and a second run sends nothing.
- Omitting `config_actions` means no save and no deploy on the fabric modules.
- The `gathered` read comes first because `merged` against a missing fabric
  tries to create it and fails on the absent BGP ASN.

### 04 - External fabric, router, link
- `nd_manage_switches` defaults to `config_actions` save and deploy true, so
  stage 04 sets both false. Monitor Mode is the second guard.
- `preserve_config: true` is required for External fabrics. No role is sent:
  the controller assigns edge-router to IOS-XE, and an omitted role is not
  enforced as drift.
- `nd_manage_switches` does not expose `max_hop` or `use_credential_for_write`.
  Its outputs carry no serial, so the stage 00 serial cross-check reads
  `/api/v1/manage/fabrics/External/switches` with `nd_rest`.
- `nd_manage_l3out` does not create links, and with `vrf_lite_auto_config:
  manual` the controller creates none. So stage 04 builds the link with
  `nd_manage_links` (`ebgpVrfLite`), against the DC fabric, which owns the
  link.
- `nd_manage_links` resolves both endpoints in their fabrics' inventories
  before any state, `deleted` included. That is why stage 04 skips the link
  when the router is skipped, and why stage 08 reads links with `gathered`
  before it deletes one.
- Omitted `template_inputs` are sent with policy defaults, for example
  `link_mtu` 9216. Always set `link_mtu`.

### 05 - L3Outs
- `interface_name` must be the sub-interface (`Ethernet1/8.2`). ND 4.2.1.10
  rejects the parent name with "Subinterface name should contain dot1q ID as
  well". The module EXAMPLES are right; its integration tests are not.
- `vrf2_name` is required even with `configured_fabrics: fabric1`. ND accepts
  the DC VRF names although the External fabric has no VRF objects (the
  router's own VRFs are named 10, 101 and 102).
- No module output carries the attach state. The L3Out GET
  (`/api/v1/manage/l3Outs?fabricName=`, from cisco.nd `EpManageL3OutsGet`)
  returns an `attach` field. Stage 05 attaches only L3Outs that are not
  attached, so a converged run reports no change.
- Updating an L3Out resets `attach` to false. Stage 05 re-attaches.
- With `attach` set, the module reports `changed` on every run, including
  check mode. Attach failures come back as warnings, so `failed_when` checks
  for "Attachment operation failed".
- `attach` only stages intent. Nothing reaches the switch until stage 06.
- Changing an L3Out's routing protocol is rejected with HTTP 400. Delete and
  recreate instead.
- `nd_manage_l3out` identifies an L3Out by name only, hence the duplicate-name
  check. Names are 1-64 characters from `[A-Za-z0-9_-]`.
- `advertise_default_route: true` reproduces the old extension template's
  `network 0.0.0.0/0` per VRF. The L3Out template already applies `route-map extcon-rmap-filter out`.
  `fabric1_details.local_asn` adds `local-as 65000` per neighbour, which is
  inert.
- An attached L3Out leaves the VRF attachment's `extensionValues` empty. The UI
  shows Extend `NONE`, and stage 02's `dcnm_vrf state: replaced` cannot strip
  it.
- The border-role check is kept from the old VRF-Lite stage. Whether an L3Out
  enforces it is undocumented.
- The address check exists because the module takes the address and the mask
  length as separate fields.
- `switch_id` is a serial on both sides, which makes the module diff exact.
- `tasks/l3out_config.yml` must build the list with a single-expression
  `set_fact` loop. The repo's `{% set %}`/`append`/`{{ out }}` idiom returns a
  list on ansible-core 2.17 but a string on newer cores.

### 06 - recalculate and deploy
- Recalculation is two calls. config-save recalculates, but every switch still
  reports In-Sync. Reading config-preview refreshes compliance, so switches
  with pending config read Out-of-Sync, which the NaC deploy role selects on.
  Without it the deploy finds nothing and reports success.
- `nd_manage_*` `config_actions` cannot replace this: it runs only after the
  module changed something, and `cisco.nd` has no config-preview endpoint. The
  stage stays on `cisco.dcnm`, because NaC's `dtc.deploy` drives it.

### 07 - verify
- The inventory, VRF, network and attachment reads use `nd_rest` against the
  legacy lan-fabric endpoints, so the whole stage runs on `cisco.nd`. `gathered` output from
  `nd_manage_switches/vrfs/networks` drops `lanAttachState`, serial and mode,
  which the report needs.
- The L3Out check runs `nd_manage_l3out` in check mode without `attach`;
  `before` is the controller's copy in input shape. The interface name is
  accepted as parent or `parent.dot1q`.
- `show bgp sessions vrf <vrf>` returns an empty string for a VRF the switch
  does not have, so a never-built fabric reads as "absent". All values are
  strings. The peer ASN is reported, not asserted.
- Sub-interfaces are read one `show interface` at a time. NX-OS rejects more
  than two ranges in one command, and `show running-config interface
  Ethernet1/8` does not include them. Genie types: `mtu` int, `first_dot1q`
  string, `ipv4` keyed by `address/prefix`.
- The unresolved-attach-group assert is deliberately not gated on
  `dc_verify_fail_on_mismatch`: an unresolvable model produces no useful
  report.
- Records for unattached switches have null fields, so lookups use
  `default(x, true)`. Hostnames are compared case-insensitively.
  `networkTemplateConfig` is JSON in a string (`from_json`). Gateways are
  compared as exact strings. Extra observed attachments are not rejected.
- Lookups take the first match; duplicates are not rejected. Roles are
  normalised with `lower | replace(' ', '_')`. Serial, mode and `ccStatus` are
  informational only.
- Evidence paths use `realpath`. The HTML layout mirrors the campus stage 12
  report.

### 08 - cleanup
- The order is: L3Outs, overlays, link, switches, fabrics, then the
  sub-interfaces on the switch.
  - Deleting a fabric leaves running config on the switch.
  - Leftover `Ethernet1/8.x` sub-interfaces are rediscovered on the next
    import, and the resource manager allocates around their dot1q tags.
  - So the switch is stripped last, after the controller has let go of it.
- Every L3Out whose `fabric1_name` is the DC fabric is removed, not only the
  declared ones. Detach comes before delete (attached-delete behaviour is
  undocumented). The detach re-sends the controller's own copy with
  `attach: false`, so cleanup does not need stage 00's files.
- The controller refuses to remove a switch with overlay attachments or a
  link, hence the order.
- Switch removal is `nd_rest` POST `.../switchActions/remove?force=true`.
  `nd_manage_switches deleted` uses the same endpoint without `force`, and an
  unforced border-leaf removal fails with "Please check Anomalies".
  `nd_rest` does not inspect HTTP 207 bodies, so `failed_when` looks for a
  per-switch `status: failed`.
- NX-OS rejects `no interface` for a sub-interface that does not exist, and one
  rejected line fails the whole `nxos_config` task. So the removal list is read
  from the device. `default interface` clears the parent.
- `nxos_config` reports changed even for ignored commands, so the result is
  read back and asserted.

## Inventory and configuration

- `group_vars/nd/connection.yml`: the upstream example reads `ND_*` environment
  variables. This repo uses vault lookups only (`ansible-automation/plugins/vars/lab_access.py`).
  Do not reintroduce environment variables.
- Timeouts of 1000 s there are load-bearing:
  - The create role's inventory step holds one request open for minutes per
    switch role.
  - With the 30 s default the call dies with "command timeout triggered". That
    looks like a credential error, because `cisco.dcnm`'s httpapi plugin
    appends "verify your login credentials".
  - `cisco.dcnm`'s own `dcnm_inventory` guard requiring timeouts of 1000 s or
    more never runs, because NaC calls that module directly.
- `group_vars/dc_fabric_switches/connection.yml`: 60 s timeouts, because five
  switches over a loaded dCloud VPN can exceed 30 s.
- The External edge router is added over the ND 4.x manage API. The legacy API
  behind `dcnm_inventory` and NaC cannot discover a non-NX-OS device.
- `collections/requirements.yml` must match the bootstrap's
  `00_scriptserver_bootstrap/roles/script_server_bootstrap/files/requirements.yml`,
  because the bootstrap does the install; a pin only here is a no-op. The
  supporting collections match `netascode/ansible-dc-vxlan-example`.
- `dc_vrf_lite.yml`:
  - Each stage reads only its part: 03 the fabric settings, 04 the link,
    05 the rows, 07 and 08 everything.
  - `vrf_lite_auto_config: back2BackAndToExternal` would allocate dot1q in its
    own order. Measured on 2026-09-27: PROD 2, MAIN 3, IOT 4, against the
    router's PROD 2, IOT 3, MAIN 4.
  - The subnet pool values and the link's IP pair are kept as defaults until
    the pod shows they can go.
  - `dot1q` is an int, because `vlan_id` is an int.
- `dc_external_settings.yml` and `dc_advanced_settings.yml`:
  - Keys are module options, passed through unchanged, so a typo fails
    Ansible's argument check.
  - `platform_type: ios-xe` selects SSH discovery; `nx-os` would take the
    SNMPv3 path, which the router does not answer.
  - `location` needs both latitude and longitude.
- `dc_switches.yml`: N9300 switches import as leaf and N9500 as spine by
  default. The spines are set explicitly, and DC-Service-Leaf must be border.
  `dc_management_default_gateway` is unverified, so it is left undefined and
  the key is omitted.

## Data model

- `global.nac.yaml`: `greenfield_cleanup: Enable` renders GRFIELD_DEBUG_FLAG
  ("Add Switches without Reload"). It does not make the import greenfield;
  NaC hardcodes `preserveConfig` false. Cisco recommends it for Nexus 9000v,
  and it saves five reloads. The VNI ranges equal the upstream defaults.
- `topology_vpc.nac.yaml`:
  - Peer-link interfaces are not declared: ND auto-detects the pair.
  - `domain_id` is allocated by ND but not reserved. That is safe only with
    one vPC pair, so pin it before adding a second.
  - vPC pairs cannot be changed in place; delete and recreate.
- `topology_switches.nac.yaml.example`: port-channel descriptions must be
  ASCII. An em dash produced HTTP 500 "unexpected error during template
  execution" for vPC 3/4/5.

## Observed on the pod, not yet explained

- Nexus Dashboard keeps a second, policy-less link `Ethernet1/8 -> Gi2`,
  discovered over CDP, beside the declared `ebgpVrfLite` link to
  `GigabitEthernet2`. It is harmless: everything stays in sync and the
  sessions come up.
- `show bgp vrf all summary` is not valid on this NX-OS release; use
  `show ip bgp summary vrf all`.

## Open questions for Cisco

- ND BU: why does an L3Out update reset `attach`? Can the module expose the
  attach state and make `attach` idempotent?
- ND BU: should a declared `ebgpVrfLite` link and the CDP-discovered link to
  the same wire coexist?
- ND BU: can `fabric1_details.local_asn` be left unset, avoiding a `local-as`
  equal to the fabric ASN?
- ND BU: does `VRF_LITE_AUTOCONFIG` or the link's IP pair matter for an L3Out,
  or can both be dropped?
- Upstream (`cisco.nd`): `nd_manage_links` resolves endpoints even for
  `deleted`; `nd_manage_switches` cannot send `force` on removal and does not
  expose `max_hop` or `use_credential_for_write`.
- NaC: issue #772 (`vxlan.routing_policies.l3out`) was closed as completed, but
  no code existed on any branch on 2026-11-12. When it lands, consider moving
  the L3Outs into the data model.
