# 2026-09-22

- **Bootstrap — the role no longer breaks when it updates itself mid-play.**
  Adding `script_server_image_owner` produced a confusing failure on the first
  run that picked it up: `'script_server_image_owner' is undefined`, pointing
  at a task whose name only existed in the new commit. Nothing was wrong with
  the variable. `sync_repo` git-pulls the very checkout that is executing, at
  step 6 of 8. Ansible loads `defaults/main.yml` **once** when the role starts,
  but `include_tasks` is dynamic and re-reads from disk, so for the rest of
  that play the new task files were paired with the previous commit's defaults.
  Any future change that adds a default and uses it after `sync_repo` would hit
  the same thing. The image tasks now resolve the owner through a `set_fact`
  with `| default(ansible_user_id, true)`, and `sync_repo` prints an explicit
  warning when the pull actually moved the checkout, saying that a later
  undefined-variable failure means nothing is broken and a re-run will clear
  it. A plain re-run was, and still is, the fix.

- **Bootstrap — the IOS-XE web root is no longer root-owned.**
  `/var/www/iosxe-images` was created `root:root 0755`, so a student who tried
  to `scp` a `.bin` straight into it got `Permission denied` and had no way
  forward except `sudo`. It is now owned by the login user
  (`script_server_image_owner`, defaulting to `ansible_user_id`, so it follows
  whoever runs the bootstrap rather than hardcoding `cisco`), and published
  images are written with that owner instead of `root`. A directory handover
  alone would not have been enough: `scp` truncates an existing file in place,
  which needs write permission on the *file*, so a new task also hands over any
  `.bin` left root-owned by an earlier run. nginx is unaffected — it reads as
  `www-data` and `0755`/`0644` still serve. Staging via the checkout plus
  `--tags image_server` keeps working exactly as before; copying into the web
  root is now simply also allowed. On a box bootstrapped before today, re-run
  `01_bootstrap_script_server.yml --tags image_server` once to take ownership.

- **Bootstrap — Python pins now have one source of truth.** `ansible-core`,
  `paramiko`, `netaddr`, both CatC SDKs and `rich` were pinned twice: once in
  `ansible-automation/requirements.txt` for `stage-script-server.sh`, and again
  as `script_server_*_version` variables feeding
  `script_server_python_packages` in the bootstrap role. The two agreed, but
  bumping one and forgetting the other would have had the role silently
  reinstall a different version over the staged one — and the evidence block
  would still have looked clean. `venv.yml` now installs from
  `requirements.txt` directly (`ansible.builtin.pip: requirements:`) and then
  adds Genie/pyATS as a second, separate task.
  `script_server_python_packages` is now just those two. Genie and pyATS stay
  out of `requirements.txt` on purpose: roughly 700 MB that is not needed to
  run `ansible-playbook`, so staging stays fast and only the bootstrap pays
  for it. A missing `requirements.txt` now fails the play with an explicit
  message instead of building an unpinned venv. Bump a shared version in
  `requirements.txt` and both paths follow.

- **Bootstrap — the end of `01` now tells you to reload your shell.** Students
  finished a clean bootstrap, read `PATH binaries: [...]` in the evidence
  block, then hit `Command 'ansible-playbook' not found` in the very same
  shell and assumed the run had failed. Nothing had: `01` appends the venv
  export to `~/.zshrc`, `~/.bashrc`, `~/.profile` and `~/.zprofile`, and a
  shell that is already open never re-reads those files. The evidence line was
  actively misleading because the check exports `PATH` inside its own task
  before calling `command -v`, so it only ever proved the binaries exist. It
  now reads "PATH binaries (resolved with the new PATH applied)" and is
  followed by an explicit **NEXT** line: run `exec $SHELL -l` or open a new SSH
  session, then `ansible-playbook --version`. The same correction is in the
  root README, the collection 00 README and the closing message of
  `stage-script-server.sh`, all of which previously said only "a new shell".

  Splunk licence stop, not a data problem.** A run today ended
  `3/5 checks passed. Failed: Nodes resolving through the device inventory
  lookup; Dashboard Studio validation.` The evidence report's own guidance
  points at `cisco.node_id` versus `evpn_device_inventory.csv` and at broken
  panel SPL; both were red herrings. Read which checks passed: the three that
  did (`systemctl is-active`, the `ss` session count, the collector's
  `otelcol_exporter_send_failed_metric_points`) never run SPL, and the two that
  failed are the only ones that search. Every query on the host returned
  `Your Splunk license expired or you have exceeded your license limit too many
  times`. `/services/licenser/localslave` showed `LocalSearch:
  DISABLED_DUE_TO_GRACE_PERIOD` against `manager_uri
  https://dcloud-lm.splunk.show:8089`, with the last successful manager contact
  on 2026-05-09 and attempts still failing, and `/services/messages` gave the
  reason: `LM__FAILED_TO_CONECT_TO_MANAGER … Signature mismatch between license
  slave … pass4SymmKey`. The lab's Splunk is a licence peer of the shared
  dCloud licence manager, and the pod was handed over without `[general]
  pass4SymmKey` reconciled, so it never checked in and the 72-hour grace period
  lapsed. Two things make this easy to misread. **Settings > Licensing shows no

  so a peer's `licenser/messages` is empty even when healthy; the real warning
  is a general splunkd message under the bell icon. And **enforcement only
  covers non-internal indexes** — `index=_internal`, `| makeresults` and
  `| inputlookup` all still work, so the instance looks alive while `index=main`
  and every `| mstats` against `evpn_assurance` return `FATAL`. Reachability is
  a red herring too — DNS resolved and TCP 8089 connected throughout. The
  telemetry pipeline itself was healthy: three switches streaming, zero HEC
  failures, `/services/data/indexes/evpn_assurance` reporting a `metric` index
  with 135,311 points and `maxTime` at the current minute, and
  `| inputlookup evpn_device_inventory.csv` returning all three nodes correctly
  domain-stripped, so the lookup join would resolve the moment search returns.
  No code change — the key is a dCloud secret and rewriting a shared
  host's `server.conf` on a guess is not a fix. The collection README now
  carries the full diagnosis under stage 08 plus two troubleshooting rows, and
  the User Guide assurance card carries a matching note telling the student to
  escalate rather than debug. Also seen on that host and worth reporting when
  escalating: `KVSTORE_PROCESS_TERMINATED`, unrelated to these five checks.

- **Stage 12 — telemetry checks reported a healthy fabric as broken.** Every
  subscription read `absent` and every receiver `no receiver`, on switches that
  answered `53 subscriptions, 53 Valid, 0 Invalid` and were streaming to the
  assurance collector at that moment. Two faults were stacked on top of each
  other.

  Subscription numbers were looked up as numbers. `genie_parse` passes the
  parsed output through JSON so Ansible can use it, and that turns every lookup
  name into text: the check asked for `40101` while the data holds `"40101"`, so
  no row matched and each fell through to its default. The tenant VLAN check
  already asked for its number as text, so this trap had been hit once before
  and never written down. Both telemetry checks now do the same, and the filter
  states the rule at the line responsible.

  That fixed the receiver check but not the subscription check. Catalyst Center
  Command Runner returns the command itself as the first line of its output, the
  way a switch echoes back what you typed. Most Genie parsers step over it; the
  `show telemetry ietf subscription all` parser treats that line as the whole
  output, finds no subscriptions in it, and reports empty — which the filter
  correctly reads as "nothing on the device". Proven by parsing the real Command
  Runner text on the script server, in the same virtual environment the playbook
  uses: with the echoed line the parser returns empty, without it all 53
  subscriptions parse and 40101 reads `Valid`. `genie_parse` now removes a first
  line that is exactly the command it was asked to parse — device echo is never
  output, so this is safe for every check.

  Stage 12 now reports **all 51 evaluated checks match the declared intent**,
  `failed=0`. Both traps are written up in the README next to the existing Genie
  note, so the next check added does not repeat them, and a troubleshooting row
  points anyone on a stale checkout at `git pull`.

- **Orchestrator — `00_site_deploy.yml` now runs the complete pipeline, 01–12.**
  Stages 11 and 12 were previously excluded, so "run the whole thing" stopped
  short of provisioning the access point and never verified the result. Both are
  now imported. Two consequences are documented at the top of the playbook and
  in both READMEs and the guide, because both can fail a run that previously
  could not: **stage 11 blocks** for up to ten minutes (`ap_wait_retries` ×
  `ap_wait_delay`) polling for an access point and then asserts, so a pod with
  no AP cabled fails there *after* the fabric is built — `-e ap_expected_count=0`
  makes the poll's `until` pass on the first attempt and skips the wait; and
  **stage 12 fails the run on any mismatch**, since `verify_fail_on_mismatch`
  defaults to `true` — `-e verify_fail_on_mismatch=false` reports instead.
  Stage 09's existing reload warning is unchanged.
