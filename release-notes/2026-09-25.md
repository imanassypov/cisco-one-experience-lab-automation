# 2026-09-25

- **02_data_center — the DC VXLAN EVPN fabric is now automated, built on Cisco
  Nexus as Code.** `02_data_center` was a one-paragraph stub naming services
  that are actually driven from other collections. It is now a working
  pipeline, `nac_vxlan/ansible/`, covering the guide's **NDFC - DC Fabric
  Deployment** section end to end: the `Pseudoco-DC1` fabric, its five
  switches and their roles, the DC-Leaf1/DC-Leaf2 vPC pair, the three server
  port-channels, and the MAIN / PROD / IOT VRFs and networks with their
  attachments.

  Built on `cisco.nac_dc_vxlan` 0.9.0 over `cisco.dcnm` 3.13.0 rather than on
  `cisco.dcnm` alone. The reason is the shape of the problem: `cisco.dcnm`
  gives one module per Nexus Dashboard object, so automating this section with
  it directly means transcribing the student's click sequence, in order, with
  every dependency between steps written out by hand. Nexus as Code takes a
  declared end state and works out the calls, which is both shorter and the
  thing that survives a change to the fabric.

  `cisco.nd` was evaluated and dropped. All 26 of its modules are
  ND-platform-level — sites, backups, Insights, `nd_rest`, `nd_version` —
  with nothing for fabrics, VRFs, networks or interfaces, so it would have
  added a dependency and a Python 3.11 floor for no capability.

  The collection lives at the same depth as `01_campus/evpn/ansible`, so
  `ansible.cfg`'s `../../../../.vault` and `../../../plugins/vars` paths are
  byte-identical to the campus ones and credentials come from the same
  vault-encrypted `lab_access.yml`. Nothing in the new tree holds a password.

- **02_data_center — laid out like `01_campus/evpn`, with one forced
  exception.** `ansible.cfg` at the collection root, `inventory/` holding
  `static_inventory.yml` and `group_vars/`, playbooks under `playbooks/`, and
  `evidence/` written beside them using the campus collection's
  `(playbook_dir ~ '/../evidence/…') | realpath` idiom. Run from the directory
  holding `ansible.cfg`, same as campus, because `ansible.cfg`'s relative
  paths to the vault and the vars plugin resolve against the working
  directory.

  The exception is `host_vars/`, which sits under `playbooks/` rather than
  under `inventory/` where Ansible's own convention would put it.
  `roles/validate/tasks/sub_main.yml` in `cisco.nac_dc_vxlan` passes the model
  location as a task-level variable, `data_path: "{{ playbook_dir }}/host_vars/{{ inventory_hostname }}"`,
  and task-level vars are beaten only by `-e`, so there is no override and the
  data model has to be a sibling of the playbooks. A symlink was considered and
  rejected: the failure mode when it is missing is an empty model, and a
  load-bearing symlink is a worse thing to hide than an unusual directory.
  `group_vars/` is plain Ansible with no collection involvement, so it does
  live under `inventory/`. Both the collection README and the inventory file
  record why.

- **02_data_center — serial number discovery is its own stage, because serials
  cannot be committed.** Nexus as Code identifies a switch by `serial_number`,
  not by hostname or management IP. That is the right identifier for a fabric
  but wrong for a shared repository: serials belong to one dCloud pod, so
  committing them would tie the checkout to a single instance and leave every
  other student's tree wrong — the same class of problem that made `lab.yml`
  gitignored on 2026-09-16.

  `00_discover_dc_switch_serials.yml` SSHes to each management address in the
  declared switch table (`group_vars/all/dc_switches.yml`) and runs
  `cisco.nxos.nxos_facts`. It is read-only with respect to the switches —
  `nxos_facts` issues show commands and nothing else — so it never pushes
  configuration to a device.

  As first written the stage printed the serials and wrote nothing, on the
  argument that transcribing them into
  `host_vars/Pseudoco-DC1/topology_switches.nac.yaml` was a deliberate manual
  step where the student saw what Nexus as Code keys a switch on.
  **That was reversed later the same day: the stage now generates that file
  itself. See the last entry below, which is the current behaviour.** What has
  not changed is that the file is gitignored with a tracked `.example` beside
  it, so it never makes a student's checkout dirty, and that the stage is not
  imported by `01_dc_deploy.yml`; if it is skipped, the orchestrator stops at
  stage 03 and says why.

  Stage 03 guards both failure modes, because the collection will not. Rule
  301 only checks that `serial_number` is non-empty, so a leftover
  `REPLACE_ME` passes validation and then fails deep inside the create role
  where the message means nothing. Stage 03 therefore refuses to start if the
  model file is missing or if any placeholder is still in it.

  Worth recording, because it is the reason this stage has to exist at all:
  the import does not use the serial. `fabric_inventory.j2` imports each
  switch by `seed_ip` with `max_hops: 0`, and `serial_number` appears there
  only inside the POAP blocks. So the collection demands a value it does not
  need for the one operation that could produce it, and a serial cannot be
  read out of the fabric until the switch is already in the fabric.

  Two findings are baked into the design. The discovery endpoint is scoped to
  a fabric, so the fabric must exist before any switch can be discovered while
  the switches are what the rest of the model needs; `02_fabric.yml` exists
  purely to break that circle, and upstream shipping a `fabric_empty_example`
  confirms a switchless fabric is a supported state. And the serials are
  written as literal text rather than as a lookup, because the validate role
  reads the model off disk in Python and never renders Jinja in it — an
  expression in a `.nac.yaml` file reaches the validator verbatim.

  It uses `dcnm_rest`, not `dcnm_inventory`. `dcnm_inventory`'s
  `update_discover_params()` filters the response down to the single entry
  matching `seedIP`, discarding the other four switches — which would look
  like a successful discovery that found one switch.

- **02_data_center — the build is greenfield by default and there is no
  confirmation gate.** The guide builds this fabric with **Preserve Config**
  unchecked, so Nexus Dashboard erases each switch's running configuration as
  it imports it, and the pipeline does the same. An earlier revision tried to
  gate this behind `-e dc_greenfield_confirm=WIPE_OK`, keyed off the declared
  `greenfield_cleanup` value. That gate has been removed because it was
  guarding the wrong thing: `preserve_config: false` is hardcoded in
  `cisco.nac_dc_vxlan`'s inventory template, so the import was always going to
  be destructive whatever the data model said, and a flag that implies
  otherwise is worse than no flag. The warning now lives in the docs instead.

- **02_data_center — `greenfield_cleanup` corrected from `Disable` to
  `Enable`.** It renders `GRFIELD_DEBUG_FLAG`, which Cisco documents as
  "Greenfield Cleanup Option — Enable to clean switch configuration without
  reload when PreserveConfig=no". That is the Advanced-tab dropdown the guide
  labels **Add Switches without Reload** and tells you to enable, and Cisco
  recommends it for Nexus 9000v fabrics, which is what this pod runs. The
  previous `Disable` was based on reading it as an equivalent of Preserve
  Config, which it is not; the practical effect of the fix is that the five
  switches no longer reload one by one during import.

  `06_remove.yml` carries a separate confirmation (`dc_remove_confirm=REMOVE_OK`)
  and is deliberately absent from `01_dc_deploy.yml`. Even when confirmed it
  leaves `inventory_delete_mode` and `link_vpc_delete_mode` off, because
  evicting switches or breaking the vPC pair is not something a routine prune
  should do — and the data model documents vPC pairs as
  provision-and-decommission only, so a broken pair has to be recreated rather
  than edited back.

- **02_data_center — verification is Nexus Dashboard API only, so it works with
  the switch VPN down.** `05_verify_fabric.yml` reads the declared intent from
  the same `.nac.yaml` files the create role consumes, so the report cannot

- **script server — `ansible-pylibssh` 1.4.0 pinned, so `network_cli` stops
  falling back to a deprecated transport.** Stage 00 of the DC collection is
  the first thing in this repo to use `ansible.netcommon.network_cli`, and it
  prints `[WARNING]: ansible-pylibssh not installed, falling back to paramiko`
  on a script server built before this pin.

  The warning is benign — `network_cli`'s `ssh_type` defaults to `auto`, it
  imports `ansible-pylibssh` if present and otherwise uses paramiko, which is
  pinned and works. The reason to fix it anyway is in netcommon's own option
  documentation: the paramiko path is **deprecated for removal in a release
  after 2028-02-01**, with an explicit instruction to migrate to libssh. So
  silencing the warning by pinning `ssh_type: paramiko` would have locked the
  lab to the transport being removed. Installing the library satisfies it
  properly and is faster, since libssh runs in-process.

  This does not repeat the `sshpass` mistake. That failure was an **apt**
  package pulling `libc6` forward until apt refused against the pinned
  `libc6-dev`. `ansible-pylibssh` publishes manylinux wheels to PyPI with
  libssh bundled (`manylinux_2_27_x86_64`, cp39 through cp314), so pip
  downloads a prebuilt binary into `~/venv` with no apt package, no compiler
  and no glibc change.

  Existing script servers need `pip install -r ansible-automation/requirements.txt`
  inside `~/venv`, or a re-run of `01_bootstrap_script_server.yml`. Until then
  the warning is cosmetic and stage 00 still collects serials.

  in the model, so forgetting is caught.

  The trade to be aware of: this is now the **only** stage in the collection
  that needs SSH to `198.18.128.x`. Everything else reaches only the Nexus
  Dashboard API and works with the switch path down.

- **02_data_center — stage 00 now generates `topology_switches.nac.yaml`
  instead of printing serials for the student to type into it.** This reverses
  the decision recorded in the serial-discovery entry earlier in this note,
  which has been annotated to point here rather than left to contradict it.
  The case for the manual step was that transcribing a serial is where the
  student learns what Nexus as Code keys a switch on. It does not survive
  contact with the failure mode it creates: rule 301 in the validate role only
  checks that `serial_number` is non-empty, so a mistyped or transposed serial
  passes validation and then fails much later inside the create role, with a
  message that names neither the serial nor the file. Copying five sixteen-
  character strings out of a terminal table by eye is exactly the work to hand
  to the machine, and what the model is keyed on is now taught by the
  generated file's own header and by the README, rather than by an error the
  student has to make first.

  After it has read the serials, the stage copies the tracked
  `topology_switches.nac.yaml.example` verbatim over
  `topology_switches.nac.yaml` and substitutes, per switch, the serial it read
  and the role declared in `inventory/group_vars/all/dc_switches.yml`.
  Substituting into a copy rather than rendering a template is deliberate:
  every comment, vPC ID and port-channel member in the example survives
  exactly as written, so the tracked file stays the readable description of
  the fabric's shape instead of decaying into Jinja. The role comes from the
  switch table and not from the example because that table is the single
  source of truth for the switch list, and taking it from anywhere else would
  let the generated model drift away from it.

  The generated file is pure build output and the stage treats it as such:
  **every run overwrites it silently, with no backup, no confirmation flag and
  no refusal if it already exists.** Its leading comment block is swapped for a
  generated-file header saying so, naming the stage that wrote it and the two
  files to edit instead — the `.example` for the shape of the model,
  `dc_switches.yml` for the switch table.

  Three checks are what make generating the file defensible, since a generator
  is only worth having if its output can be trusted without inspection. The
  stage asserts that every declared switch returned a serial *before* it
  writes anything, so an `UNREACHABLE` switch fails the run with nothing on
  disk and a partial model never reaches stage 03. The substitution is
  anchored on each `- name: <switch>` line rather than on list position, so
  reordering either source is harmless. And because an anchored regex that
  matches nothing is not an error to `ansible.builtin.replace` — it leaves the
  file alone and reports no change — the stage slurps the file back afterwards
  and asserts that no `REPLACE_ME` survived, that every serial it read is
  present, and that each switch carries its own serial and its declared role.
  A switch name that disagrees between `dc_switches.yml` and the `.example` is
  caught there rather than shipped into stage 03.

  One implementation detail worth recording because it is not obvious: the
  replacement uses `\g<1>` and `\g<2>`, not `\1` and `\2`. Nexus serial numbers
  can begin with a digit, and `\1` immediately followed by a `9` parses as
  group 19.

  Stage 03 keeps its own placeholder guard, because the file is on disk and
  nothing stops it being edited after the fact; its message now says the file
  is generated and to re-run stage 00, rather than telling you to transcribe.
  The generated file stays gitignored and the `.example` stays tracked, with
  the `.gitignore` comment updated to call it build output. Updated in the
  same pass: the stage 00 and `01_dc_deploy.yml` headers, the `dc_switches.yml`
  header, both READMEs and the student guide. All eight playbooks pass
  `ansible-playbook --syntax-check`.
