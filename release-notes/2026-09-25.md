# 2026-09-25

- **02_data_center — the DC VXLAN EVPN fabric is now automated, built on Cisco
  Nexus as Code.** `02_data_center` was a one-paragraph stub naming services
  that are actually driven from other collections. It is now a working
  pipeline, `nac_vxlan/ansible/`, covering the guide's **NDFC - DC Fabric
  Deployment** section end to end: the `Pseudoco-DC1` fabric, its five
  switches and their roles, the DC-Leaf1/DC-Leaf2 vPC pair, the three server
  port-channels, and the MAIN / PROD / IOT VRFs and networks with their
  attachments.

  Built on `cisco.nac_dc_vxlan` 0.9.0 over `cisco.dcnm` 3.13.0 rather than on
  `cisco.dcnm` alone. The reason is the shape of the problem: `cisco.dcnm`
  gives one module per Nexus Dashboard object, so automating this section with
  it directly means transcribing the student's click sequence, in order, with
  every dependency between steps written out by hand. Nexus as Code takes a
  declared end state and works out the calls, which is both shorter and the
  thing that survives a change to the fabric.

  `cisco.nd` was evaluated and dropped. All 26 of its modules are
  ND-platform-level — sites, backups, Insights, `nd_rest`, `nd_version` —
  with nothing for fabrics, VRFs, networks or interfaces, so it would have
  added a dependency and a Python 3.11 floor for no capability.

  The collection lives at the same depth as `01_campus/evpn/ansible`, so
  `ansible.cfg`'s `../../../../.vault` and `../../../plugins/vars` paths are
  byte-identical to the campus ones and credentials come from the same
  vault-encrypted `lab_access.yml`. Nothing in the new tree holds a password.

- **02_data_center — laid out like `01_campus/evpn`, with one forced
  exception.** `ansible.cfg` at the collection root, `inventory/` holding
  `static_inventory.yml` and `group_vars/`, playbooks under `playbooks/`, and
  `evidence/` written beside them using the campus collection's
  `(playbook_dir ~ '/../evidence/…') | realpath` idiom. Run from the directory
  holding `ansible.cfg`, same as campus, because `ansible.cfg`'s relative
  paths to the vault and the vars plugin resolve against the working
  directory.

  The exception is `host_vars/`, which sits under `playbooks/` rather than
  under `inventory/` where Ansible's own convention would put it.
  `roles/validate/tasks/sub_main.yml` in `cisco.nac_dc_vxlan` passes the model
  location as a task-level variable, `data_path: "{{ playbook_dir }}/host_vars/{{ inventory_hostname }}"`,
  and task-level vars are beaten only by `-e`, so there is no override and the
  data model has to be a sibling of the playbooks. A symlink was considered and
  rejected: the failure mode when it is missing is an empty model, and a
  load-bearing symlink is a worse thing to hide than an unusual directory.
  `group_vars/` is plain Ansible with no collection involvement, so it does
  live under `inventory/`. Both the collection README and the inventory file
  record why.

- **02_data_center — serial number discovery is its own stage, because serials
  cannot be committed.** Nexus as Code identifies a switch by `serial_number`,
  not by hostname or management IP. That is the right identifier for a fabric
  but wrong for a shared repository: serials belong to one dCloud pod, so
  committing them would tie the checkout to a single instance and leave every
  other student's tree wrong — the same class of problem that made `lab.yml`
  gitignored on 2026-09-16.

  `02_discover_serials.yml` does what the student does in section 4 of the
  guide, over the API: seeds a CDP crawl at `198.18.128.101`, two hops, and
  joins the result back to the declared switch table in
  `group_vars/all/dc_switches.yml` on management IP. On a re-run it reads the
  serials straight from `switchesByFabric` and skips the crawl. It is
  read-only throughout — `test-reachability` reports what is discoverable, it
  does not import anything — so it is safe to run at any time.

  **It prints the serials and writes nothing.** Transcribing them into
  `host_vars/Pseudoco-DC1/topology_switches.nac.yaml` is a deliberate manual
  step: it is where the student sees what Nexus as Code actually keys a switch
  on, and generating the file would hide exactly that. The file is gitignored
  with a tracked `.example` to copy from, so a student's edits never make the
  checkout dirty. The practical consequence is that a first `00_dc_deploy.yml`
  run stops at stage 03 and asks for the file; the second run goes end to end.

  Stage 03 guards both failure modes, because the collection will not. Rule
  301 only checks that `serial_number` is non-empty, so a leftover
  `REPLACE_ME` passes validation and then fails deep inside the create role
  where the message means nothing. Stage 03 therefore refuses to start if the
  model file is missing or if any placeholder is still in it.

  Worth recording, because it is the reason this stage has to exist at all:
  the import does not use the serial. `fabric_inventory.j2` imports each
  switch by `seed_ip` with `max_hops: 0`, and `serial_number` appears there
  only inside the POAP blocks. So the collection demands a value it does not
  need for the one operation that could produce it, and a serial cannot be
  read out of the fabric until the switch is already in the fabric.

  Two findings are baked into the design. The discovery endpoint is scoped to
  a fabric, so the fabric must exist before any switch can be discovered while
  the switches are what the rest of the model needs; `01_fabric.yml` exists
  purely to break that circle, and upstream shipping a `fabric_empty_example`
  confirms a switchless fabric is a supported state. And the serials are
  written as literal text rather than as a lookup, because the validate role
  reads the model off disk in Python and never renders Jinja in it — an
  expression in a `.nac.yaml` file reaches the validator verbatim.

  It uses `dcnm_rest`, not `dcnm_inventory`. `dcnm_inventory`'s
  `update_discover_params()` filters the response down to the single entry
  matching `seedIP`, discarding the other four switches — which would look
  like a successful discovery that found one switch.

- **02_data_center — the build is greenfield by default and there is no
  confirmation gate.** The guide builds this fabric with **Preserve Config**
  unchecked, so Nexus Dashboard erases each switch's running configuration as
  it imports it, and the pipeline does the same. An earlier revision tried to
  gate this behind `-e dc_greenfield_confirm=WIPE_OK`, keyed off the declared
  `greenfield_cleanup` value. That gate has been removed because it was
  guarding the wrong thing: `preserve_config: false` is hardcoded in
  `cisco.nac_dc_vxlan`'s inventory template, so the import was always going to
  be destructive whatever the data model said, and a flag that implies
  otherwise is worse than no flag. The warning now lives in the docs instead.

- **02_data_center — `greenfield_cleanup` corrected from `Disable` to
  `Enable`.** It renders `GRFIELD_DEBUG_FLAG`, which Cisco documents as
  "Greenfield Cleanup Option — Enable to clean switch configuration without
  reload when PreserveConfig=no". That is the Advanced-tab dropdown the guide
  labels **Add Switches without Reload** and tells you to enable, and Cisco
  recommends it for Nexus 9000v fabrics, which is what this pod runs. The
  previous `Disable` was based on reading it as an equivalent of Preserve
  Config, which it is not; the practical effect of the fix is that the five
  switches no longer reload one by one during import.

  `05_remove.yml` carries a separate confirmation (`dc_remove_confirm=REMOVE_OK`)
  and is deliberately absent from `00_dc_deploy.yml`. Even when confirmed it
  leaves `inventory_delete_mode` and `link_vpc_delete_mode` off, because
  evicting switches or breaking the vPC pair is not something a routine prune
  should do — and the data model documents vPC pairs as
  provision-and-decommission only, so a broken pair has to be recreated rather
  than edited back.

- **02_data_center — verification is Nexus Dashboard API only, so it works with
  the switch VPN down.** `06_verify_fabric.yml` reads the declared intent from
  the same `.nac.yaml` files the create role consumes, so the report cannot
  drift from what was deployed, and compares it against
  `switchesByFabric` plus the top-down VRF, network and attachment endpoints.
  No device SSH. It writes `evidence/stage06-verification.md` in the same shape
  as the campus stage 12 report and fails on mismatch unless
  `-e dc_verify_fail_on_mismatch=false`.

  The check that matters most is `lanAttachState`: an attachment sitting in
  `PENDING` means intent exists on the controller and never reached the switch,
  which is exactly the failure mode that a "deployment succeeded" message hides.
  Config compliance is reported when the controller supplies it but is not
  asserted on, because `ccStatus` does not appear anywhere in `cisco.dcnm`
  3.13.0 and asserting on an unverified key would produce false failures.

- **02_data_center — the upstream collection's own examples are stale, and the
  README says so.** `tests/integration/host_vars/examples/` inside
  `cisco.nac_dc_vxlan` 0.9.0 still uses the pre-1.0 flat shape:
  `vxlan.global.name`, `vxlan.global.bgp_asn`,
  `vxlan.underlay.general.subnet_mask`. The current model is
  `vxlan.fabric.name` / `vxlan.fabric.type`, `vxlan.global.ibgp.bgp_asn` and
  `vxlan.underlay.ipv4.subnet_mask` — confirmed against
  `roles/validate/files/defaults.yml`, `plugins/plugin_utils/data_model_keys.py`
  and the deprecation path in `prep_001_fabric.py`, which explicitly describes
  the flat keys as retained for backwards compatibility.

  This is worth more than a footnote because of how the collection fails.
  `schema_path` defaults to empty and the fallback schema does not exist, so
  schema validation is **skipped with a warning** and only the Python rules
  run. A key that is misspelled or in the wrong place is therefore dropped
  silently rather than rejected. Following the shipped examples would have
  produced a model that validated cleanly and built the wrong fabric.

- **02_data_center — VRF-Lite and the edge router are deliberately not
  automated, and the README explains why rather than omitting them.** The
  guide's sections 8 and 9 extend MAIN, PROD and IOT out of DC-Service-Leaf to
  `DC-SITE11-CEDGE8Kv`. That router is out of scope for this pipeline, so
  `07_external_fabric.yml` creates the External fabric object as a switchless
  container and nothing more — which means it delivers no connectivity on its
  own, and the README says that plainly instead of implying coverage.

  Separately, Nexus as Code's `overlay_extensions.vrf_lites` is not the same
  feature as the guide's step. It models per-switch BGP/OSPF routing policy for
  an extension that already exists (it renders `ndfc_vrf_lite_ebgp.j2`, its
  rules sit under `roles/validate/files/rules/external/`), whereas the guide
  performs an `EXTEND: VRF_LITE` attachment with auto-allocated dot1q tags and
  IFC addressing. No shipped example pairs the two. Recorded as a spike to run
  against the live appliance rather than guessed at. The guide's
  Resources-tab settings that go with it — `Back2BackAndToExternal`, the
  `192.168.252.0/24` DCI subnet, Auto Deploy for Peer, Auto Allocation of
  Unique IP — have no key in the 0.9.0 data model at all, and that is recorded
  too.

- **pins — `cisco.nac_dc_vxlan` 0.9.0 and `cisco.dcnm` 3.13.0 added to the
  bootstrap, with the Python dependencies they actually need.** Both pins are
  in `00_scriptserver_bootstrap/.../files/requirements.yml` as well as the new
  collection `requirements.yml`, identical in both, because the bootstrap file
  is the one that gets installed — a higher pin in a collection file alone is
  silently never applied, which is the trap `cisco.catalystcenter` fell into on
  2026-09-15.

  ND 4.2.1 support landed in `cisco.dcnm` 3.12.1 and `cisco.nac_dc_vxlan` 0.9.0
  requires `>= 3.13.0`, so 3.13.0 is a floor rather than a preference.
  `ansible-automation/requirements.txt` gains `nac-yaml==1.0.0`,
  `nac-validate==1.0.0`, `macaddress`, `packaging`, `jmespath` and `requests`:
  the collection reads and validates the data model in Python, so these are
  hard runtime dependencies, not optional extras. The two pinned versions are
  the ones the collection's own `requirements.txt` pins. All six confirmed to
  exist on PyPI and to be compatible with the repo's `ansible-core==2.17.14`
  (`requires_ansible: ">=2.15.0,<2.19.0"`).
