# 2026-09-27

- **02_data_center — the pipeline deploys before stage 05 and again after it,
  and stage 05 waits for the controller.** `01_dc_deploy.yml` imports the
  stages as `02, 03, 04, 06, 05, 06, 07`, so the numbers on the files are no
  longer the order they run in. Nexus Dashboard builds the VRF-Lite
  inter-fabric connection itself, from `VRF_LITE_AUTOCONFIG`, during a
  Recalculate and Deploy and only once the edge router stage 04 adds is in the
  External fabric. The first deploy is therefore what produces the `VRF_LITE`
  extension prototype on `Ethernet1/8` that stage 05 needs; the second pushes
  the sub-interfaces and BGP neighbours stage 05 stages. This is the
  deploy-edit-deploy sequence the manual guide describes, which the pipeline
  had dismissed as a UI artefact. Operationally: a re-run has no external
  connectivity between the two deploys, because stage 02's `state: replaced`
  clears the extension and the first deploy pushes that removal.

  Verified on the pod — the same stage 05 command reported
  `Prototype extensionType(s) returned: []` before any deploy and
  `Controller offers 1 VRF_LITE extension prototype(s)` after one, attaching
  PROD, IOT and MAIN with the declared dot1q tags and addresses. The link the
  controller built carries `SOURCE`
  `Pseudoco-DC1_AUTO_CONFIG_IFC_VRFLITE_955T6I5X2D4` and
  `AUTO_VRF_LITE_FLAG: true`, so it was auto-created — and against a
  **non-Nexus** peer, with the IOS-XE template `ios_xe_Ext_VRF_Lite_Jython`,
  which Cisco's "Auto IFC is supported on Cisco Nexus devices only" guideline
  says should not happen. What that guideline still governs is the far side:
  the controller will not configure the router.

  `dc_vrf_lite_retries` (default 6) and `dc_vrf_lite_delay` (default 20) exist
  and the precheck uses them, so it waits two minutes for a link the controller
  may still be finishing; `-e dc_vrf_lite_retries=12` waits longer.
  **Correction to earlier today:** commit `ef7f222` deleted that retry loop on
  the strength of one run in which a successful deploy was followed by a
  failing stage 05, which looked like proof that waiting could never help; it
  was instead a single observation that did not generalise, and the loop is
  reinstated. The distinction worth keeping is that waiting cannot *substitute*
  for the deploy, but the deploy's effect is not instantaneous either.

- **02_data_center — the VRF-Lite sub-interfaces are pinned to an explicit MTU,
  which is what makes the deploy after stage 05 succeed.** Without it the
  deploy fails with `Delivery failed with message: MTU of sub-interface greater
  than parent interface detected`. The parent `Ethernet1/8` is 9000, taken from
  the inter-fabric link's `Link MTU`; the sub-interfaces were asking for 9216.
  That
  9216 is neither a `cisco.dcnm` default nor a fabric setting — it is the
  `else` branch of the controller's own `Default_VRF_Extension_Universal`
  template, which renders `if (@ITEM.MTU != "") { mtu @ITEM.MTU } else { mtu
  9216 }` and takes the fallback because **`dcnm_vrf` has no MTU key**: its
  `vrf_lite` suboptions are only `peer_vrf`, `interface`, `ipv4_addr`,
  `neighbor_ipv4`, `ipv6_addr`, `neighbor_ipv6` and `dot1q`. Clicking through
  the UI never hits this, because the prototype the controller offers already
  carries `"MTU":"9000"` and the dialog writes it through. New
  `dc_vrf_lite_mtu` in `inventory/group_vars/all/dc_vrf_lite.yml`, applied by
  `05_vrf_lite.yml` with a `POST` to
  `top-down/fabrics/<fabric>/vrfs/attachments` after the module runs. The
  parent is left at 9000 rather than raised to 9216 deliberately: the External
  fabric is in Monitor Mode, so the controller cannot correct the far end, and
  an MTU mismatch does not fail a deploy — it fails later, on large packets.
  **This bullet first shipped with the value 9000 and the claim that it matched
  the router; both were wrong.** See the correction later in this file for what
  the router actually reports and what the value is now.

- **02_data_center — new read-only diagnostic,
  `playbooks/diagnose_vrf_lite.yml`.** Deliberately unnumbered so nobody
  mistakes it for a build stage. Every call is a GET, so it is safe to run at
  any point and safe to re-run. It prints the raw prototype list, every link in
  both fabrics with its `templateName`, the `Ethernet1/8` interface record, the
  VRF attachment states and both fabrics' access mode. Run it when stage 05
  fails and read section 1 first. New variable
  `dc_vrf_lite_peer_interface: GigabitEthernet2` exists only so the diagnostic
  can query the inter-fabric link by switch pair; nothing is written to the
  peer.

- **02_data_center — `DC-Service-Leaf` is now in the data model's `dc_leaves`
  attach group, so stage 02 owns the plain VRF attachment.** It had been left
  out on the reasoning that attaching the border leaf without its extension was
  worse than not attaching it. That was wrong about the sequence: the manual
  guide's section 8 has two Detach/Attach sliders per VRF, and the plain
  attachment is the first half of the job rather than a broken version of it.
  Stage 05 is now the second slider and nothing else. Operationally this means
  a create run keeps the border leaf's attachment and clears only the
  extension, where it used to remove both — so stage 05 must still run after
  stage 02 on every pass, for a narrower reason. A missing attachment on the
  border leaf is now a real `missing_switches` failure in stage 07 rather than
  a tolerated `NA`.

- **02_data_center — `dc_vrf_lite_mtu` is corrected from 9000 to 1500, because
  the reason given for 9000 was not true.** The comment in
  `inventory/group_vars/all/dc_vrf_lite.yml`, the collection README, this file
  and the student guide all said 9000 matched `mtu 9000` on the edge router's
  `GigabitEthernet2`. It does not. `show interfaces GigabitEthernet2` on
  `DC-SITE11-CEDGE8Kv` reports `MTU 1500 bytes`, and `show ip interface` on
  `GigabitEthernet2.2`, `.3` and `.4` reports `MTU is 1500 bytes` on all three;
  none of them carries an `mtu` or `ip mtu` line, so they inherit the parent's
  1500. The 9000 was the controller's `Link MTU` on the inter-fabric link -
  a different number that the field name *"Interface MTU on both ends of VRF
  Lite IFC"* made easy to mistake for the router's. Operationally the old
  value created the exact mismatch its own comment claimed to avoid: the eBGP
  sessions would still have come up, because TCP picks the lower MSS of the
  two ends, so nothing obvious would have failed while any transit packet over
  1500 bytes was silently dropped at the router. 1500 is still well inside the
  switch's 576-9216 range and still below the parent's 9000, so the deploy
  continues to pass.
