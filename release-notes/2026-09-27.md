# 2026-09-27

- **02_data_center — stage 05's retry loop is gone, because the thing it waited
  for never arrives by waiting.** `05_vrf_lite.yml` no longer retries its
  `dcnm_vrf` call, and `dc_vrf_lite_retries` / `dc_vrf_lite_delay` no longer
  exist. The stage needs Nexus Dashboard to already be offering the border leaf
  a `VRF_LITE` extension prototype on `Ethernet1/8`, which exists only where a
  VRF-Lite inter-fabric connection terminates; `dcnm_vrf` reads that list at
  `dcnm_vrf.py` lines 5126-5127 and fails at line 4721 with `No VRF LITE
  capable interfaces found on this switch` when nothing in it has
  `extensionType VRF_LITE`. Proof it is not a timing problem: a full successful
  `06_recalculate_and_deploy.yml` (5/5 switches, `in_sync=True`) was followed
  immediately by a byte-identical stage 05 failure. Do not re-run hoping for a
  different answer, and do not reach for Recalculate and Deploy.

- **02_data_center — stage 05 now reads that precondition before it writes, so
  the failure names the cause.** A read-only GET against
  `top-down/fabrics/<fabric>/vrfs/switches` runs first and reports what the
  controller is offering. Skip it with `-e dc_vrf_lite_precheck=false` to see
  the module's own error instead.

- **02_data_center — new read-only diagnostic,
  `playbooks/diagnose_vrf_lite.yml`.** Deliberately unnumbered so nobody
  mistakes it for a build stage. Every call is a GET, so it is safe to run at
  any point and safe to re-run. It prints the raw prototype list, every link in
  both fabrics with its `templateName`, the `Ethernet1/8` interface record, the
  VRF attachment states and both fabrics' access mode. Run it when stage 05
  fails and read section 1 first. New variable
  `dc_vrf_lite_peer_interface: GigabitEthernet2` exists only so the diagnostic
  can query the inter-fabric link by switch pair; nothing is written to the
  peer.

- **02_data_center — `DC-Service-Leaf` is now in the data model's `dc_leaves`
  attach group, so stage 02 owns the plain VRF attachment.** It had been left
  out on the reasoning that attaching the border leaf without its extension was
  worse than not attaching it. That was wrong about the sequence: the manual
  guide's section 8 has two Detach/Attach sliders per VRF, and the plain
  attachment is the first half of the job rather than a broken version of it.
  Stage 05 is now the second slider and nothing else. Operationally this means
  a create run keeps the border leaf's attachment and clears only the
  extension, where it used to remove both — so stage 05 must still run after
  stage 02 on every pass, for a narrower reason. A missing attachment on the
  border leaf is now a real `missing_switches` failure in stage 07 rather than
  a tolerated `NA`.

- **docs — the student guide's card 7 is rewritten, and its anchor changed from
  `#why-stage-05-runs-twice` to `#what-stage-05-needs`.** The card was titled
  "VRF-Lite, and the Wait That Replaced a Deploy" and taught the retry loop and
  the removed `-e dc_vrf_lite_retries=12` flag; it is now "VRF-Lite, and the One
  Thing It Needs" and documents the IFC precondition, both wrong explanations
  and the evidence that killed each, and the diagnostic to run. Any bookmark or
  external link to the old anchor needs updating. `CHANGELOG.md`'s consolidated
  entry carried the same stale claim and was corrected in place.
