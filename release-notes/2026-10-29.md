# 2026-10-29

- **swim — golden tagging moved from the floor to the building.** Stage 09.2
  tagged the image at the project's floor path. Catalyst Center accepts a floor
  siteId and reports success, but the 3.1 Images tab can only navigate to areas
  and buildings, so the tag was written into a scope the UI could neither show
  nor manage: the 9300 family read "missing standard image" at every selectable
  scope, with no way to clear it. Nothing caught it, because the per-device
  `goldenImages` view *does* see a floor tag — so `image_state.yml` and every
  09.x assert passed over a broken tag. Measured on the pod before the fix: the
  Site-105 building reported `goldenImageCount` 0 while the MAIN floor reported
  1. Tagging and upgrading are now separate scopes, both derived from the
  project's `Hierarchy*` fields: the **building** is tagged, the **floor** is
  resynced, distributed to and activated. Re-tagging at the parent *moves* the
  tag rather than duplicating it, so no untag step is needed — attempting one
  fails with `NCSW10395: An inheritted tag cannot be un-tagged`.

- **swim — two new guards in 09.2.** `tag_scope_check.yml` refuses to tag at a
  floor before the call is made, and `tag_verify.yml` re-reads
  `siteWiseProductNames` for the site afterwards and fails if it reports no
  standard image for the family. This converts a silent, UI-only failure into a
  stage failure. Both read through `uri` with the stage's auth token, and accept
  HTTP 202 — several SWIM-adjacent endpoints answer 202 with a full body.

- **settings — images moved to a top-level `swim_catalog`.** Image definitions
  lived inside each project's `swim` block, so a second device type at the same
  site had nowhere to go and every path was spelled out by hand. Images are now
  declared once under `swim_catalog.images[]` with an `id`, and a project opts
  in with `swim: {enabled, images: [ids]}`. The `site_name` key is gone.
  Stage 09 fails loudly on an unknown id, on an enabled site that names no
  image, and on two entries sharing one `.bin`.

- **swim — the C9800-CL wireless controller is now upgraded.** DC-Site-10 gains
  a `swim` reference to `c9800-26.02.01`
  (`C9800-CL-universalk9.26.02.01.SPA.bin`, rollback
  `C9800-CL-universalk9.17.12.02.SPA.bin`). Identifiers measured on the
  appliance: SWIM family `Cisco Catalyst 9800-CL Wireless Controller for Cloud`,
  inventory family `Wireless Controller`, series
  `Cisco Catalyst 9800 Wireless Controllers for Cloud`.
  **Activation is default-on, like the switches, and that controller serves the
  Site-105 access points** — in a full `00_site_deploy.yml` build the reload
  lands before stage 11 waits for the APs, but running stage 09 alone after the
  APs have joined will drop them. Stage 09 now says so before it starts.
  Four `.bin` files must be staged on the script server, not two.

- **swim — `-e swim_images=<id>` limits a run to one device type.** With a
  switch image and a controller image both enabled, there was no way to upgrade
  the switches without also reloading the C9800 short of editing
  `settings.json` and putting it back. The new override takes `swim_catalog`
  ids, comma-separated, and defaults to empty (everything enabled). A value
  that matches nothing fails the stage rather than quietly upgrading nothing.

- **swim — the role's four REST lookups now use native collection modules.**
  `tag_scope_check`, `tag_verify`, the repository check in 09.2 and
  `image_state` called `ansible.builtin.uri` with a hand-built
  `X-Auth-Token` header. They now use `sites_info`,
  `site_wise_product_names_info`, `swim_image_details_info` and
  `network_device_images_info`, which return the same
  `catalystcenter_response.response` payload. This removes the auth header from
  task results entirely — the structural cause of the token leak above — along
  with the manual `status_code: [200, 202]` handling and the role's dependency
  on `_catc_token`, so `09_swim.yml` no longer imports `catc_common/auth_token`.
  Note the `*_info` modules reject `catalystcenter_log` /
  `catalystcenter_log_level`, which the workflow managers accept, so the
  playbook now carries two `module_defaults` anchors.

- **collections — `cisco.catalystcenter` pinned to 2.14.0.** Requires
  ansible-core >= 2.16 (we pin 2.17) and adds a `pytz` import, now in
  `ansible-automation/requirements.txt`; a collection's Python dependencies are
  never installed automatically. `swim_workflow_manager` grew ~1,800 lines
  between 2.11.0 and 2.14.0 and `site_workflow_manager` is byte-identical.
  The three pin files had already drifted — `requirements.yml` 2.11.0,
  bootstrap 2.11.0, jumphost 2.10.2 — and are now all 2.14.0.
  Verified on the pod: stages 01, 02 and 09 produce the same recaps as on
  2.11.0 (01 `ok=81 changed=0`, 02 `ok=39 changed=0`, 09 `ok=52 changed=4
  failed=0`). Stages 02 and 07 touch this collection only through `sites_info`.
  Both module docs still ask for `catalystcentersdk >= 3.1.6.0.2` /
  `>= 3.2.3.0.0` while the project pins `3.1.3.0.1`; that gap predates this
  change and the modules work regardless, so the SDK pin is unchanged.

- **swim — dropped the preflight resync and both compliance runs.** Stage 09 had
  five forward phases; it now has three. The 09.1 inventory resync was measured
  doing nothing — `lastUpdated` was byte-identical before and after, and the
  module returned "No inventory actions were performed in Cisco Catalyst
  Center" (with `force_sync: true` as well) while the role printed "resynced".
  A control that reports success without acting is worse than no control. The
  baseline IMAGE compliance was never compared against anything, and the
  post-activation one asserted only that a scan had executed, not that any
  device was compliant. None of the three gated anything. What proves an
  upgrade landed is the `DEVICE_UP_TO_DATE` check inside distribute/activate
  and stage 12; Catalyst Center re-collects each device itself as it completes
  an activation, so there is nothing to refresh afterwards. Removes
  `preflight.yml`, `postcheck.yml`, the `swim_run_preflight`,
  `swim_run_postcheck` and `swim_sync_device_config` knobs, the
  `swim_preflight` / `swim_postcheck` tags, and the
  `inventory_workflow_manager` / `network_compliance_workflow_manager`
  dependencies. Saves ~73s per run.

- **swim — phases renumbered and tasks explicitly indexed.** Phases are now
  contiguous: 09.1 import_and_tag, 09.2 distribute, 09.3 activate, 09.4
  rollback. Every task carries its position (`09.1.1`, `09.1.2`, …), and tasks
  contributed by a guard file nest under the step that includes them
  (`09.1.7.3`) so inserting one cannot renumber its caller. `image_state.yml`
  runs inside two phases, so it takes its prefix from the caller via
  `_swim_step`; its index trails the task name because `ansible-lint`
  `name[template]` requires the Jinja expression to be the last thing in the
  string. `ansible-lint` passes at the `production` profile.

- **docs — stage 09 reference rewritten for the catalog model.** Separate
  `swim_catalog` and `project[].swim` tables, the tag-scope rule, the wireless
  outage warning, and five new troubleshooting rows. The stage 09 playbook
  header no longer claims the import source is CCO and no longer numbers its own
  phases 11.1–11.6.
