# 2026-10-29

- **swim — golden tagging moved from the floor to the building.** Stage 09.2
  tagged the image at the project's floor path. Catalyst Center accepts a floor
  siteId and reports success, but the 3.1 Images tab can only navigate to areas
  and buildings, so the tag was written into a scope the UI could neither show
  nor manage: the 9300 family read "missing standard image" at every selectable
  scope, with no way to clear it. Nothing caught it, because the per-device
  `goldenImages` view *does* see a floor tag — so `image_state.yml` and every
  09.x assert passed over a broken tag. Measured on the pod before the fix: the
  Site-105 building reported `goldenImageCount` 0 while the MAIN floor reported
  1. Tagging and upgrading are now separate scopes, both derived from the
  project's `Hierarchy*` fields: the **building** is tagged, the **floor** is
  resynced, distributed to and activated. Re-tagging at the parent *moves* the
  tag rather than duplicating it, so no untag step is needed — attempting one
  fails with `NCSW10395: An inheritted tag cannot be un-tagged`.

- **swim — two new guards in 09.2.** `tag_scope_check.yml` refuses to tag at a
  floor before the call is made, and `tag_verify.yml` re-reads
  `siteWiseProductNames` for the site afterwards and fails if it reports no
  standard image for the family. This converts a silent, UI-only failure into a
  stage failure. Both read through `uri` with the stage's auth token, and accept
  HTTP 202 — several SWIM-adjacent endpoints answer 202 with a full body.

- **settings — images moved to a top-level `swim_catalog`.** Image definitions
  lived inside each project's `swim` block, so a second device type at the same
  site had nowhere to go and every path was spelled out by hand. Images are now
  declared once under `swim_catalog.images[]` with an `id`, and a project opts
  in with `swim: {enabled, images: [ids]}`. The `site_name` key is gone.
  Stage 09 fails loudly on an unknown id, on an enabled site that names no
  image, and on two entries sharing one `.bin`.

- **swim — the C9800-CL wireless controller is now upgraded.** DC-Site-10 gains
  a `swim` reference to `c9800-26.02.01`
  (`C9800-CL-universalk9.26.02.01.SPA.bin`, rollback
  `C9800-CL-universalk9.17.12.02.SPA.bin`). Identifiers measured on the
  appliance: SWIM family `Cisco Catalyst 9800-CL Wireless Controller for Cloud`,
  inventory family `Wireless Controller`, series
  `Cisco Catalyst 9800 Wireless Controllers for Cloud`.
  **Activation is default-on, like the switches, and that controller serves the
  Site-105 access points** — in a full `00_site_deploy.yml` build the reload
  lands before stage 11 waits for the APs, but running stage 09 alone after the
  APs have joined will drop them. Stage 09 now says so before it starts.
  Four `.bin` files must be staged on the script server, not two.

- **docs — stage 09 reference rewritten for the catalog model.** Separate
  `swim_catalog` and `project[].swim` tables, the tag-scope rule, the wireless
  outage warning, and five new troubleshooting rows. The stage 09 playbook
  header no longer claims the import source is CCO and no longer numbers its own
  phases 11.1–11.6.
