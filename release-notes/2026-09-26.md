# 2026-09-26

- **02_data_center — the verify stage could not pass on a correct fabric, and the crash
  it started with was hiding the reason.** `05_verify_fabric.yml` failed
  outright in `Compare networks` with `The task includes an option with an
  undefined variable` and, inside it, `'None' has no attribute 'split'` out of
  `(a.portNames | default('')).split(',')`. Nexus Dashboard returns `portNames`
  as JSON `null` on some attachment records - the key is present and its value
  is null - and Jinja's `default('')` substitutes only for an *undefined* value,
  never for `None`. It reads `default('', true)` now, which is boolean mode and
  substitutes for anything falsy. Worth carrying to anything else that reads a
  controller response: a present-but-null field is precisely the case plain
  `default()` does not cover.

  Behind the crash sat the bug that mattered. The attachment endpoints
  enumerate every switch that *could* carry a VRF or a network and report the
  ones the controller has not attached with `isLanAttached: false` and
  `lanAttachState: NA`, and the stage was folding those `NA` strings into its
  "every attachment must be DEPLOYED" test. `DC-Service-Leaf` is deliberately
  absent from the attach group in `vrfs.nac.yaml`, because attaching the VRFs
  to it belongs to the VRF-Lite step the data model cannot express, so all
  three VRFs and all three networks failed on every single run. A healthy
  fabric reported itself broken, which means the stage's verdict could not be
  trusted either way. It now partitions on the `isLanAttached` boolean, judges
  only the genuinely attached records, and names the rest under a new **Not
  attached** column in both report tables. It was **not** weakened into
  ignoring anything that is not `DEPLOYED`: an attached switch in `PENDING` or
  `OUT-OF-SYNC` still fails, which is the fault the stage exists to catch.

  Ignoring the `NA` rows on their own would have made the VRF attachment check
  vacuous, since a VRF attached to nothing would then look like one attached
  everywhere it was declared. So VRFs gained a declared-versus-attached switch
  check they never had, resolving each VRF's `vrf_attach_group` through
  `vxlan.overlay.vrf_attach_groups` and reporting anything missing under
  "Switches missing"; the comparison is case-insensitive because the controller
  is inconsistent about case. Networks already had the equivalent in their
  switch-and-port pairs. Verified live on the pod: the verify stage reports
  **11 of 11 check(s) match intent** with `failed=0`, where with only the crash
  fixed it had reported 5 of 11.

- **02_data_center — a typo in an attach group name made the verify stage.s strongest
  check vacuous while the report still said yes.** Each VRF names a
  `vrf_attach_group` and each network a `network_attach_group`, resolved by
  name against the groups declared in the same file. A name that matched
  nothing resolved to an empty switch list, so "Switches missing" and
  "Attachments missing" came out empty and both of those arms passed having
  proved nothing - a VRF attached to one leaf out of two was reported as a
  pass. Measured, not theorised: with `MAIN` naming a nonexistent `dc_leafs`,
  the old stage reported `11 of 11 check(s) match the declared intent` with
  `failed=0`. `05_verify_fabric.yml` now asserts every named group resolves,
  before its first API call, listing every offending object and the groups the
  file does declare, under a message beginning `DATA MODEL ERROR, not a fabric
  fault` so nobody goes looking at the switches. Naming no group at all is
  untouched, since such an object already fails its own row on "at least one
  switch attached", and the guard is deliberately not gated on
  `-e dc_verify_fail_on_mismatch=false`: that flag means report the mismatch
  instead of failing, and a model the stage cannot resolve yields no report
  worth showing. The correct data model is unaffected - verified live on the
  pod, `failed=0` and still **11 of 11 check(s) match intent**.

- **02_data_center — both DC READMEs rewritten as a student guide rather than a
  debug log.** The two files had grown to 138 and 692 lines, and most of the
  larger one was the history of how each bug had been found: a suspected
  non-ASCII HTTP 500 with its supporting Cisco links, the VLAN collision with
  `cisco.dcnm` source quoted by line number, a connection-timeout diagnosis, a
  `'None' has no attribute 'split'` traceback, and a sixteen-row troubleshooting
  table of error strings. That is valuable history and it is already recorded
  here and in `git log`, but it was crowding out the thing a network engineer
  opening the README actually needs, which is what the fabric is and how to
  build it.

  They are now 85 and 303 lines and follow the student guide's own structure.
  The collection README opens on what the pipeline builds, mapped section by
  section onto guide sections 4, 5 and 6, with the resulting fabric's switches,
  VRFs, networks and gateways in a table. Then how Nexus as Code works,
  prerequisites, how to run it, the eight playbooks and what the numbering
  means, the data model file by file, why serial discovery is its own stage,
  what the verification stage proves and how to read its report, and where the
  automation deliberately stops.

  Nothing operational was dropped in the process. Every rule a reader has to
  follow survives, stated as a rule instead of as the story of the failure that
  taught it: pin `vlan_id` on any VRF or network you add, from the 2000-2299
  and 2300-2999 ranges; keep the data model ASCII, because these values are
  rendered into device configuration by controller-side templates; no Jinja in
  a `.nac.yaml`; check a key exists before inventing one, since there is no
  schema and a misspelling is dropped silently; vPC pairs are provision and
  decommission only. The same is true of the two surprises in a first run,
  which are now stated as expected behaviour under "Running it": stage 02
  erases the running configuration of all five switches with no prompt, and its
  import step runs for minutes with no output while the controller discovers
  them.

- **process — the four-agent documentation pipeline is opt-in instead of
  automatic.** `.cursor/rules/change-pipeline.mdc` required every change to a
  playbook, role, inventory or data model to fan out to four subagents in three
  waves. In practice that cost more time than it saved on small changes, so the
  default is now to make the change directly and write the README and release
  note as part of it. The agents are still specified in full, with their file
  ownership boundaries and briefing checklist, and run when asked for.

  The review wave's checks survive as a self-check list to run directly, plus
  two things learned the hard way. `grep '[^\x00-\x7F]'` is useless for finding
  non-ASCII on macOS: BSD grep does not interpret `\x` escapes, so the pattern
  becomes a negated set of the literal characters `\ x 0 - 7 F`, matches nearly
  every line of prose, and can never fail. It has already produced one false
  green here; use `rg` or a Python byte scan. And a subagent briefed with live
  evidence already in hand, a captured payload or an exact error string, is
  doing implementation rather than discovery, which is most of the difference
  between a useful agent and a slow one.

- **02_data_center — new stage `03_advanced_settings.yml` applies the seven
  fabric settings Nexus as Code has no key for.** `cisco.nac_dc_vxlan` 0.9.0
  cannot express the guide's Resources tab, and that was not cosmetic: **VRF
  Lite Deployment** was left at `Manual`, which tells Nexus Dashboard never to
  auto-create a VRF-Lite inter-fabric link, so the pipeline produced a fabric
  that looked complete and could not be extended to the edge router. The stage
  now declares `VRF_LITE_AUTOCONFIG` `Back2Back&ToExternal`,
  `AUTO_SYMMETRIC_VRF_LITE` and `AUTO_UNIQUE_VRF_LITE_IP_PREFIX` on,
  `DCI_SUBNET_RANGE` `192.168.252.0/24` with `DCI_SUBNET_TARGET_MASK` 30, plus
  License Tier `premier` and Telemetry off. Values live in the new
  `inventory/group_vars/all/dc_advanced_settings.yml`; the playbook holds none
  of its own.

  **The settings turned out to live in two different places, and a read-only
  GET of the live fabric was what established it.** The five VRF-Lite settings
  are fabric nvPairs and go in through `cisco.dcnm.dcnm_fabric`. License Tier
  and Telemetry are not nvPairs at all - neither name appears among the
  fabric's 423 of them - but properties of the Nexus Dashboard 4.2 fabric
  object at `/api/v1/manage/fabrics/<fabric>`, as `licenseTier` and
  `telemetryCollection`, alongside a camelCase mirror of the nvPairs. That
  object has no partial update, so the stage does a read-modify-write on it
  with `dcnm_rest`. The GET for that has to happen **after** the `dcnm_fabric`
  task, or the mirror would put the pre-change VRF-Lite values straight back.

  Three properties worth recording. `state: merged` cannot revert stage 02:
  on ND 4.x the module rebuilds the payload from the controller's own nvPairs
  before overlaying the declared changes, because a partial fabric update is
  rejected, and an unknown key fails with `Key <name> not found in fabric
  configuration` rather than being dropped. The stage is idempotent with
  natural YAML types, because `dcnm_fabric` normalises a boolean to
  `"true"`/`"false"` and an integer to its string form before comparing
  against the controller. And `dcnm_rest` always reports `changed: false`
  whatever it did, so the PUT carries an explicit `changed_when`.

  Verified live on the pod: first run `changed=2`, License Tier `essentials` →
  `premier`; second run `changed=0` with both halves reporting "already matched
  the declared intent, nothing sent"; and Nexus as Code's own settings intact
  afterwards - `BGP_AS` 65000, `GRFIELD_DEBUG_FLAG` Enable, `RR_COUNT` 2,
  `L2_SEGMENT_ID_RANGE` 30000-49000, `L3_PARTITION_ID_RANGE` 50000-59000, the
  anycast gateway MAC and every VLAN range unchanged.

  **"Add Switches without Reload" is deliberately not in the new data model.**
  It is the `GRFIELD_DEBUG_FLAG` nvPair and Nexus as Code does model it, as
  `vxlan.global.ibgp.greenfield_cleanup` in `global.nac.yaml`, already set to
  `Enable`. Two files setting one nvPair is how configuration drifts, so this
  stage carries only what the model genuinely cannot say. The stale note in
  `global.nac.yaml` that called these settings an open spike now points at
  their real home, and its `Back2BackAndToExternal` was corrected to the
  controller's own spelling, `Back2Back&ToExternal`.

- **02_data_center — stage 03 also sets the fabric's Location, and Nexus
  Dashboard turns out to have no field for the place name.** Added `location`
  to `dc_advanced_nd_fabric_settings`, bringing the stage to eight settings.
  The request was "San Jose, US", and it lands as `latitude: 37.3382`,
  `longitude: -121.8863` because coordinates are all the controller stores:
  there is no city, country or address key on the fabric object, in its
  `management` sub-object, or among the fabric's 423 nvPairs - grepped, not
  assumed. The UI's location picker geocodes what you type and keeps only the
  two numbers, then drops a pin on the fabric map. So the place name survives
  only as a comment beside the coordinates in the data model, and the comment
  says why it has to.

  No playbook change was needed, which is the useful part: `location` is a
  property of the same Nexus Dashboard fabric object as License Tier and
  Telemetry, so the existing read-modify-write picked it up unaltered. Both
  coordinates must be declared together, because the stage combines
  non-recursively and a partial `location` would replace the whole object and
  leave the other coordinate at zero.

  Verified live on the pod, including the case a nested value could have
  broken: the fabric object went from `{"latitude": 0, "longitude": 0}` to the
  declared pair on the first run with `changed=1`, and a second run's fresh
  GET found no drift and sent nothing, so the controller stores the floats
  back unrounded and the stage stays idempotent.
