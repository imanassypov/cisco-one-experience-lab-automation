# 2026-09-24

- **Docs — the guide now tells students to reload their shell after the
  bootstrap.** Step 4 of card 1 had the two bootstrap commands with their full
  `~/venv/bin/` path, and a 🛑 callout warning not to let apt install
  `ansible-core` — but it never said what to do instead, and every command from
  Step 5 onward silently switches to a bare `ansible-playbook`. The missing
  piece was the reload: `01_bootstrap_script_server.yml` puts `~/venv/bin` on
  `PATH` by writing to the shell startup files, and a shell that is already open
  never re-reads them, so `ansible-playbook` stays "command not found" in that
  session. A clean, successful bootstrap therefore looks broken.

  This exact failure was fixed on 2026-09-22 in the root README, the collection
  00 README and the closing message of `stage-script-server.sh`. The student
  guide was not on that list and kept the gap.

  Step 4 now carries an explicit reload step — `exec $SHELL -l` then
  `ansible-playbook --version`, or open a new SSH session — states that the
  bootstrap worked and the shell has simply not caught up, and says the
  `~/venv/bin/` prefix can be dropped from there on, which is what the rest of
  the guide assumes. The apt warning now points at the reload instead of only
  forbidding the wrong fix.

  Checked by sweeping every `ansible-playbook` invocation in the whole file
  rather than reading the one card: the only full-path uses are the two
  bootstrap commands in Step 4, and the venv-repair callout in card 3 where the
  explicit path is the point. All 30 others are bare, consistent with the new
  instruction.

  `iosxe_images/`, `image_base_url`, or port `8080`. A student following only

- **Docs — the image transfer was described in the wrong order.** Card 1 Step 5
  told students to `scp` the images into `iosxe_images/` in the checkout and then
  re-run `01_bootstrap_script_server.yml --tags image_server` to publish them.
  That sequence made no sense where it sat: Step 4 has *already* bootstrapped the
  host, so nginx is running and `/var/www/iosxe-images` already exists — created
  owned by the login user precisely so it can be written to without `sudo`.
  Following the guide as written meant transferring roughly 2.6 GB over the VPN,
  then copying it a second time on the host, then re-running a playbook, to reach
  a state that a single `scp` would have produced.

  Step 5 now sends the images straight to `/var/www/iosxe-images/` and says
  plainly that there is no publish step and no playbook to re-run. The checkout
  route is kept as the secondary case it actually is — staging *before* the first
  bootstrap so everything completes in one pass — and the note records that the
  two cannot conflict, because the publish task is an additive per-file copy that
  never clears the web root. Verified in `http_image_server.yml`: the web root is
  created `owner: script_server_image_owner`, existing `.bin` files are handed to
  that user so `scp` can truncate in place, and publishing is
  `ansible.builtin.copy` looped over whatever `find` returned.

  The same corrected sequence is now in `iosxe_images/README.md` (as a
  which-folder-when table), the campus README's stage 09 prerequisites, and the
  root README.

- **Assurance troubleshooting — evidence that distinguishes a refused licence
  from a network fault.** Re-verified the stage 08 `3/5` fault live and found
  the write-up leaned on one reading where three were available. The collection
  README now records that the licence manager *replies* with the signature
  rejection, which proves the pod reaches it and the failure is a refused login
  rather than a connectivity problem, and that `licenser/licenses` returning
  zero installed licences with no active group in `licenser/groups` confirms
  the host holds no entitlement of its own. Added a timestamp table because
  `first failure time=` inside the licence message counts only from the last
  splunkd restart — it showed 2026-09-22 two days ago and 2026-09-24 today for
  one unbroken fault. Confirmed the mechanism from `/services/messages`, where
  all five messages carry a `timeCreated_iso` within three seconds of each
  other: a startup sequence, not five faults arriving together. The README now
  says to date the outage from `last_manager_contact_success_time` and from the
  hourly retry count in `index=_internal component=LMTracker`, which survives
  restarts and showed roughly 60 failures an hour all day. Anyone reading the
  message alone would conclude the fault had just appeared. Diagnosis and remediation are unchanged: pod fault,
  escalate for the dCloud key.

- **Assurance troubleshooting — KV Store failing after the deploy playbook is an
  expired certificate, not the app install.** The deploy role ends with
  `splunk restart`, so `KVSTORE_FAILED` and `KVSTORE_PROCESS_TERMINATED` surface
  moments after the playbook finishes and read as though installing the app
  broke something. mongod's own log gives the reason: `InvalidSSLConfiguration`
  on `/opt/splunk/etc/auth/mycerts/server.pem`, expired 2026-07-22 and still in
  place on 2026-09-24. mongod validates its certificate only at startup and
  never re-checks while running, so the expiry stayed invisible for two months
  until the first restart — which happened to be this playbook. Confirmed the
  timing from `index=_internal`: two splunkd starts and six KV Store failures in
  thirty days, all on the same day, against a certificate that expired well
  before either. The app ships no `collections.conf` and does not touch KV Store
  at all. The collection README now carries a dedicated section with mongod's
  error, the `server.conf` inheritance (`[kvstore]` sets no `sslKeysPath`, so it
  uses `[sslConfig] serverCert`), an `openssl s_client` one-liner that reads the
  expiry off port 8089 without host access, and the two searches that separate
  trigger from cause. Impact is low — telemetry, indexing, dashboards and the
  CSV lookup are unaffected, and the playbooks disable certificate validation —
  so it is pod health to escalate, not a pipeline failure.

- **Assurance troubleshooting — why repointing the expired certificate is more
  dangerous than it looks.** Checked whether Splunk's own generated certificate
  could stand in for the expired one. It can, on dates: `auth/server.pem` is
  `CN=SplunkServerDefaultCert`, valid to 2028-06-17, against the in-use
  `auth/mycerts/server.pem` that expired 2026-07-22. But the two differ in a way
  that decides the outcome. The pod's certificate carries a plain
  `BEGIN PRIVATE KEY`, so `sslPassword` is inert today; Splunk's default carries
  a `BEGIN ENCRYPTED PRIVATE KEY`, so repointing `[sslConfig] serverCert` makes
  that password load-bearing and a wrong value stops splunkd starting at all —
  trading a degraded KV Store for a dead Splunk on a shared host. The README now
  warns against that and points at `[kvstore] sslKeysPath` instead, which is
  absent from `server.conf` and is precisely why KV Store inherits the broken
  certificate; a mistake there is confined to KV Store. Also recorded that on a
  pod carrying the licence fault as well, fixing KV Store buys nothing because
  search is still refused and stage 08 stays at 3/5, so both should be escalated
  together. The 2028 date on the default certificate shows the intended build
  lifetime, which makes the custom one lapsing after a year the anomaly.
